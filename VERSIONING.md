# Версионирование и теги релизов

Инструкция по закреплению версий (тегов) для сайта мемориального направления.

## Последовательность действий

1. Добавьте изменения в индекс и сделайте коммит:

   ```powershell
   git add dist/
   git commit -m "chore: publish built site from dist"
   ```

2. Создайте аннотированный тег на этом коммите:

   ```powershell
   git tag -a v1.0.0 -m "Первая публикация мемориального сайта"
   ```

3. Отправьте ветку и теги в SourceCraft:

   ```powershell
   git push sourcecraft main
   git push sourcecraft --tags
   ```

4. Отправьте зеркало на GitHub:

   ```powershell
   git push origin main
   git push origin --tags
   ```

## Семантическое версионирование (SemVer)

Формат версии: `MAJOR.MINOR.PATCH`

| Версия | Когда ставить |
|---|---|
| `v1.0.0` | Первый полноценный релиз |
| `v1.0.1` | Мелкие правки / исправления |
| `v1.1.0` | Новая функциональность (обратимо совместимая) |
| `v2.0.0` | Крупные изменения (несовместимые) |

## Важный нюанс для мемориального сайта

Если в будущем сайт будет меняться часто (добавление имён, памятных записей), не обязательно каждый раз поднимать `MAJOR` или `MINOR`. Можно:

- делать релизы реже — например, по значимым вехам: `v1.0.0`, затем `v1.1.0`;
- или использовать точечные версии для мелких правок: `v1.0.0` → `v1.0.1`.

Главное — тег ставится **на коммит после того, как изменения уже зафиксированы**, тогда история будет чистой и понятной.

## Примечание

- Тег — это ссылка на конкретный коммит. Если сделать тег до коммита, он «повиснет» на старом состоянии без изменений.
- Аннотированный тег (`git tag -a`) хранит автора, дату и сообщение — это правильная практика для релизов. Лёгкий тег (`git tag v1.0.0` без `-a`) такими данными не обладает.
- `git push --tags` отправляет все локальные теги. Если нужен только один: `git push <remote> v1.0.0`.
